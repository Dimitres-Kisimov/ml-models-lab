# Model card: sku-text-classifier

## Model details

- **Type:** fastText-style linear classifier over hashed character n-grams
  (Joulin et al. 2016; feature hashing per Weinberger et al. 2009).
  Implemented in plain PyTorch in
  [`mllab/sku_text_classifier/model.py`](../../mllab/sku_text_classifier/model.py);
  the tokenizer/hasher is pure Python
  ([`hashing.py`](../../mllab/sku_text_classifier/hashing.py)) and unit-tested.
- **Pipeline:** lowercase -> regex sub-token split of alphanumerics
  (`M8x40` -> `m8`, `x40`, `8`, `40`) -> boundary-marked char n-grams (3-5,
  e.g. `<m8`, `m8>`) -> deterministic 64-bit FNV-1a hash into 2^17 buckets ->
  `nn.EmbeddingBag(mode="mean")`, dim 24 -> linear softmax over 12 classes.
- **Size:** **3,146,028 trainable parameters**, ~3.15M of which are the
  2^17 x 24 hashed embedding table; the classification head itself is 300
  parameters. Counted from the instantiated module.
- **Training config:** full-batch Adam, lr 0.5, 60 epochs, seed 5;
  cross-entropy with **inverse-frequency class weights**; 75/25 stratified
  train/test split.
- **One improvement over the base method:** the sub-token split of part
  numbers before hashing, so an unseen SKU code is represented by its *shape*,
  plus the class weighting for rare categories.

## Intended use

- Demonstrate cheap, vocabulary-free categorisation of short catalogue
  descriptions (assign one of 12 known product categories) - a portfolio
  exhibit and a template for supplier-feed enrichment where new part numbers
  arrive constantly.
- **Out of scope:** open-set classification (it can never say "none of the
  12"), real supplier feeds without label-quality auditing, non-Latin or
  non-English text (the tokenizer regex only captures `[a-z]`/digit runs), and
  any compliance-relevant classification (customs codes, hazard classes) where
  an error has legal consequences.

## Training data

- Synthetic, generated by `mllab.synth.make_sku_text(seed=5)`: 12 categories x
  300 templated descriptions (3,600 rows; 2,700 train / 900 test). Each string
  samples a category core phrase, an optional shared material (steel, brass,
  ...), an optional shared brand, and optional size tokens (`M{d}x{d}`,
  `{d}mm`, `PN{dddd}`), with randomized word order and dropout of optional
  tokens.
- **Assumptions baked in:** classes are exactly balanced (300 each), labels
  are noise-free, and category core words always appear. The
  deliberate cross-category vocabulary overlap (materials, brands, sizes)
  makes the task non-trivial, but real catalogue text is far messier:
  misspellings, abbreviations, multilingual fragments, and *wrong labels*.
- Deterministic under the seed (tests enforce this).

## Evaluation

- **Metric: macro-F1** on the stratified test split, with a row-normalised
  confusion matrix. Why: the portfolio's KPI rule is to use the metric that
  survives class imbalance; macro-F1 weights every category equally, so a
  classifier cannot look good by nailing frequent classes and dumping rare
  ones. (On this balanced synthetic set accuracy happens to coincide with
  macro-F1 - both 0.963 - but on the imbalanced real feeds this is built for,
  they diverge, which is why macro-F1 is the reported number.)
- **Measured (seed 5, printed by `python -m mllab.sku_text_classifier`):**
  macro-F1 **0.963** vs a majority-class baseline of **0.013** (accuracy
  reference: 0.963).

## Limitations and failure modes

- **Never abstains, and OOV inputs fail silently:** hashing means a
  completely out-of-domain string ("office chair", an empty scan artifact, a
  serial number) still maps to buckets and still gets argmax-assigned one of
  the 12 categories - with no confidence threshold, no "unknown" class, and
  no calibration of the softmax anywhere in the pipeline. An input with no
  extractable token is mapped to bucket 0 by construction (`hash_document`
  guarantees one feature) and classified anyway.
- **Hash collisions are unaudited:** unrelated n-grams share buckets in a
  2^17 table by design; on this small vocabulary that is harmless, but a real
  catalogue with millions of distinct n-grams shifts the collision rate, and
  there is no measurement of collision-induced error here.
- **The measured 0.963 is a ceiling, not an estimate:** train and test come
  from the *same* templating process. Template-generated regularities (core
  phrase always present, fixed size-token formats) do not hold on real data;
  a real-feed macro-F1 would need to be re-measured, not extrapolated.
- **12 fixed classes:** adding a category means retraining and re-splitting;
  there is no incremental mechanism.

## Ethical and deployment considerations

Category assignments look administrative but carry money and safety
consequences downstream: category drives pricing rules, tax/duty treatment,
and in an MRO catalogue sometimes safety-relevant filtering (adhesives and
aerosols carry handling rules that bolts do not). Because this classifier
always outputs a confident-looking label - even for garbage input - deploying
it without an abstain threshold would convert its silent failure mode into
mis-priced or mis-handled products. A deployment should add a
minimum-confidence gate with human review below it, audit label quality on a
stratified sample before training (supplier-fed labels are noisy, and a clean
score on dirty labels is meaningless), and re-measure macro-F1 per category so
that a rare-but-critical category's failures are not averaged away.
